\begin{abstract}
\noindent
Split inference runs the first $k$ layers of a neural network on a
microcontroller and sends the intermediate activation tensor to a server, which
runs the rest. We built the whole pipeline on three ESP32-class boards of
different power and measured what the choice of $k$ costs. Over 3{,}813 requests
with no corrupted deliveries, sending everything to the server was faster than
every split point on every board: $5.1\times$ faster on an ESP32-S3 and
$15.5\times$ faster on an ESP32-CAM. The weakest board could not host a split
point at all. Cutting deeper made things worse, not better: the deeper cut
shrank the tensor from 4{,}668\,B to 888\,B, but it saved only 2.7\,ms of
transfer while adding 26--164\,ms of inference on the device. The per-stage
breakdown explains why. Compute on the device is two orders of magnitude larger
than anything else, while transfer, the very thing split inference is meant to
reduce, takes 7--12\,ms no matter which cut produced it. A sensitivity analysis
over the measured stages puts break-even at a server $51\times$ slower than
ours.
\end{abstract}

\section{The question}

For a network layer $k$, a split deployment pays three costs: running the first
$k$ layers on the device, sending the resulting activation tensor, and running
the rest on the server. Cutting later means more work on the device and usually
fewer bytes on the air. Split inference assumes that some middle value of $k$
beats both extremes, and that the best $k$ depends on the device.

This report tests that assumption by measuring it. It does not learn or adapt
the split point: every policy here is a fixed rule, and the exhaustive sweep is
the baseline an adaptive orchestrator would have to beat.

All boards run ESP-IDF v5.5.3 with TensorFlow Lite Micro. The server is the same
machine that builds the firmware: it runs the Wi-Fi access point (2.4\,GHz,
because ESP32 radios have no 5\,GHz band), the orchestrator, and the second half
of the inference. Its CPU is capped to 400\,MHz and the process is pinned to
four cores. Section \ref{sec:threats} explains what that costs the conclusions.

\subsection{Model and split points}

MobileNetV2, width multiplier 0.35 (every layer keeps 35\% of the channels of
the reference network, which is what makes it small enough for an MCU),
$96\times96\times3$ input, full-int8 post-training quantization, two classes.
Heads and tails are cut from one set of weights at the flatbuffer level (the
\texttt{.tflite} file format itself, so operators and weights are copied
byte-for-byte instead of being retrained or re-quantized), and the quantization
parameters of the boundary tensor are copied unchanged from the head output to
the tail input. A test checks that the int8 logits of $\mathrm{full}(x)$ and
$\mathrm{tail}_k(\mathrm{head}_k(x))$ are bit-identical over 200 random int8
inputs at every cut, so a split deployment provably returns the same prediction
as full offload. Accuracy is therefore the same by construction, and latency is
the only thing that differs between policies.

Three split points: \texttt{k0} (no split: the JPEG goes to the server, which
runs the whole model), \texttt{k\_shallow} (after inverted-residual block 2,
boundary tensor $24\times24\times8 = 4{,}608$\,B), and \texttt{k\_deep} (after
block 6, $6\times6\times24 = 864$\,B).

\subsection{Transport and measurement}

UDP with fragmentation at the application level, CRC32 per tensor, NACK-based
selective repeat over three rounds, and an abort path. One asyncio process on
the server sends at most one request per node at a time. Every request writes one
SQLite row that splits end-to-end latency into five stages that do not overlap
and add up exactly to the total: \texttt{device} (flash read plus head
inference), \texttt{uplink}, \texttt{queue}, \texttt{server}, \texttt{residual}.
Every number in this report comes from a query over those rows.

\section{Method}

There are two kinds of run. The \emph{sweep} measures every feasible
\emph{(node, cut)} pair, 200 requests each, one node at a time. Running one node
at a time is what makes the numbers describe the cut itself rather than whatever
the other nodes happened to be doing. The \emph{policy runs} then test four fixed
rules with the whole fleet active: \texttt{k0}, \texttt{k\_shallow},
\texttt{k\_deep}, and \texttt{best}, which replays the per-node winner from the
sweep.

Every board reads the same 50 images from flash, in the same order, so all
policies see the same inputs.

Seven gates guard the procedure, and each one invalidates everything after it if
it fails. They cover split correctness, ARQ integrity under injected loss,
verification of the whole harness against simulated nodes, arena feasibility per
tier, fleet stability, sample counts, and dispatch correctness.

\section{Results}

\subsection{Which split points each board can host}

A board can only host a head if it can fit that head's \emph{arena}: the single
block of RAM that TensorFlow Lite Micro reserves at startup and reuses for every
intermediate tensor of a model. It is allocated once and never grows, so the
size it needs is known before the model runs, and a board with less free RAM
than that simply cannot run the head.

\centering
\begin{tabular}{llrrl}
\toprule
Tier & Arena source & \texttt{k\_shallow} & \texttt{k\_deep} & Feasible cuts \\
\midrule
A & 8\,MB octal PSRAM   & 149{,}972\,B & 158{,}120\,B & \texttt{k0}, \texttt{k\_shallow}, \texttt{k\_deep} \\
B & 8\,MB quad PSRAM    & 142{,}296\,B & 150{,}396\,B & \texttt{k0}, \texttt{k\_shallow}, \texttt{k\_deep} \\
C & 100\,KB internal    & \multicolumn{2}{c}{needs 138{,}240\,B, has 98{,}480\,B} & \texttt{k0} only \\
\bottomrule
\end{tabular}
\caption{Arena needed per head, measured on the device at boot. Tier C is short
by 39\,KB and cannot host any head: its firmware links none.}
\label{tab:feasibility}
\end{table}

There are two results here. First, the weakest board cannot split, so on that
hardware the only available policy is full offload. Second, the same cut needs a
different amount of arena on different silicon: 149{,}972\,B on the S3 against
142{,}296\,B on the ESP32, for the same weights and tensor shapes, because the S3
build uses vector kernels that allocate their own scratch memory.

\subsection{Bytes on the air}

Sending the image costs fewer bytes than sending the tensor from the shallow cut,
which is not what intuition suggests. The reason is that the image is compressed
and the tensors are not. The raw $96\times96\times3$ input is 27{,}648\,B, and
JPEG takes it down to 1{,}775\,B; the activation tensor at \texttt{k\_shallow} is
4{,}608\,B of uncompressed int8, six times smaller than the raw input but still
$2.6\times$ larger than the JPEG. Only once the network has downsampled a few
more times does the activation drop below the compressed image, which is what
happens at \texttt{k\_deep}.

The \texttt{device} stage dominates every split cut, and nothing else comes
within two orders of magnitude. At the same time \texttt{uplink} barely changes

driven by per-packet overhead rather than by bytes, so the data inflation in
Table~\ref{tab:bytes} is real but costs almost no time.

\section{Threats to validity}
\label{sec:threats}

The server is an x86 laptop, not an MCU-class edge box, and even capping the CPU to 400\,MHz 
and limiting the cores, kept the results very cler towards one direction. For a better comparison,
more edge devices should be used, such that more workload is put on the server, making local inference more competitive.

The input is done over stored images, not live capture. In a real scenario, the edge should also 
take in account for the reading and processing time of the input data.

\section{Conclusion}

No split point beat full offload on any board, cutting deeper made things worse,
and the weakest board could not split at all. Inference on the device dominates
the budget by two orders of magnitude, while transfer stays roughly constant
across cuts, so the parameter this project set out to tune has almost no effect.
The negative result is quantified rather than just asserted: the server would
have to be $51\times$ slower before the shallow cut broke even.
